# GraphRAGとは

> 出典: [GraphRAGを実際に動かしてみた！仕組みやメリットとデメリット、RAGとの違いを徹底解説 | WEEL](https://weel.co.jp/media/tech/about-graphrag/)

## 定義

GraphRAG（Graph Retrieval-Augmented Generation）は、2024年2月にMicrosoft Researchが発表した技術。
従来の RAG に知識グラフ（ナレッジグラフ）を組み合わせ、「ノード（対象）とエッジ（関係）で表現された
構造化データを活用することで、より高度な検索と回答生成を実現する手法」。

## RAGとの主要な違い

| 項目 | RAG | GraphRAG |
|------|------|---------|
| データ構造 | テキスト集合をベクトル化 | グラフDB内のノード・エッジ構造 |
| 検索方式 | ベクトル類似度ベース | グラフクエリでパス探索 |
| 強み | 単純な情報検索 | 関係性や因果関係の把握 |
| クエリ柔軟性 | キーワード列中心 | 構造化クエリも可能 |
| 回答の特性 | テキスト片の集合 | 網羅的で一貫性のある回答 |

従来のベクトル検索型RAGは、複数文書にまたがる「点と点をつなぐ推論」や、
データセット全体を俯瞰する要約的な質問に弱いという課題がある。

## 仕組み（2段階）

### 1. インデックス作成フェーズ
- テキストを小さなチャンクに分割
- LLMでエンティティ・関係・重要記述を自動抽出
- 知識グラフを構築し、コミュニティ検出を実施
- 各コミュニティの要約文を生成

### 2. クエリ処理フェーズ
- **グローバル検索**: 全体的な質問に対してコミュニティサマリーを活用
- **ローカル検索**: 特定エンティティを起点に隣接関係を辿る
- **ハイブリッド検索**: 全文検索＋ベクトル検索も組み合わせる

## メリット

1. 見落としのない検索（間接的な繋がりも捉えられる）
2. 文脈理解（背景知識を踏まえた回答）
3. 異種データ統合（記事・論文・SNSなど複数ソースを一構造で処理）
4. 複雑な推論・包括的要約への対応力
5. 数百万トークン規模でも網羅的な回答が可能

## デメリット

1. 実装が複雑（グラフDB設計・LLM活用の専門知識が必須）
2. コスト負担が大きい（LLM解析費用・計算資源・応答時間の増加）
3. グラフの精度がLLMの抽出精度に依存（誤抽出→誤答リスク）
4. 複数処理ステップのため回答生成が遅くなりがち
5. 単純な質問には過剰な処理になりうる

## 実装方法（3つの主流）

### Microsoft公式パッケージ「graphrag」
```bash
python -m pip install graphrag
graphrag init
# inputディレクトリに文書を配置
python -m graphrag index --root .
```

### Neo4j公式「neo4j-graphrag-python」
```bash
pip install neo4j-graphrag neo4j openai
```
Neo4j上のグラフデータとLLMを組み合わせ、関係性を考慮した検索・生成を実装する。

### LangChain + Neo4j（GraphCypherQAChain）
質問 → LLMがCypherクエリを自動生成 → Neo4jで実行 → 回答生成、という流れ。
例: 「未解決のチケットは何件？」→ `MATCH (t:Task {status: 'open'}) RETURN COUNT(t)`

誤クエリ生成のリスク低減には、システムメッセージでのクエリ生成誘導や出力検証が有効。

## 活用分野

- 医療: 症状→疾患→治療法の体系化、複雑症例の網羅的推論
- 法律: 判例・法令の引用関係グラフ化、関連判例の自動検索
- 科学研究: 遺伝子・タンパク質相互作用ネットワーク解析
- ソーシャル分析: ユーザー関係のグラフ化によるキーパーソン・コミュニティ特定

## まとめ

GraphRAGは複雑な関係性を扱う場面で威力を発揮するが、実装難度とコストが課題。
プロジェクトの目的に応じて通常の[[RAGとは|RAG]]との使い分けが重要。
